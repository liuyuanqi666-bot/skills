# 分房名单整理

## 核心要求

执行“基础信息预检、详细核对、分房确认、制表、二次复核、最终汇报”的封闭流程。

在用户明确确认资料和分房方案以前，禁止开始填表、生成草稿文件或替用户猜测。发现任何缺失、歧义、冲突或规则未覆盖的情况时，立即停止制表，集中列出问题并等待用户答复。

## 工作流程

### 1. 首先执行基础信息预检

先检查当前对话、附件、游客信息表、模板顶部信息和领队护照照片，确认以下五类基础信息：

- 团号。
- 领队姓名；用户明确确认本团无领队或导游时记录为“无”。
- 人数，必须能区分游客人数和领队人数，例如 `28+1`。
- 航班信息，至少包含去程和回程的航班号、出发地、目的地及时间。
- 领队信息：中文姓名、英文姓名、性别、出生日期、出生地、护照号、签发日期、签发地、有效期和联系电话。

用户明确确认本团无领队或导游时，领队姓名和证件资料不再是缺项。此时人数写为“游客数+0”，去除顶部“领队：”栏，与旁边人数栏合并，不生成 `TL` 人员行，不得删除该栏。

航班信息默认必须写成：`{去程航班号} {去程出发地简称}→{去程目的地简称} （{起飞时间}-{到达时间}）；{返程航班号} {返程出发地简称}→{返程目的地简称} （{起飞时间}-{到达时间}）`。

例如：`9C8569 上海浦东→济州 （07:45-10:05）；9C8568 济州→上海浦东 （21:35-22:15）`。除非用户明确要求，不添加日期、“去程/回程”、机场全称或航站楼。用户提供格式参考截图时，将截图同时视为版式依据，不得只提取其中的数据。

信息可能来自用户文字，也可能分散在表格、模板和图片中。先查完所有已提供来源，再判断是否缺失；不要重复询问已经能够可靠读出的内容。

用户提供领队护照照片时：

1. 直接目视检查证件资料页，并与机器可读区 MRZ 交叉核对姓名、护照号、出生日期、性别和有效期。
2. 提取中文姓名、英文姓名、性别、出生日期、出生地、护照号、签发日期、签发地和有效期。
3. 护照通常不显示联系电话；用户没有另行提供领队电话时，必须询问，不得留空、猜测或使用其他游客电话。
4. 照片存在模糊、反光、裁切、遮挡、分辨率不足或字符无法唯一判断时，明确指出看不清的字段，并请用户补发清晰照片或文字。
5. 图片正文与 MRZ、图片与用户文字、不同图片之间存在冲突时，列出冲突值并询问以哪个为准。
6. 不得从姓名或照片外观推断性别；以证件字段或用户明确说明为准。

只要上述五类基础信息中有一项缺失、不清晰或冲突，就立即停止后续整理，一次性列出缺项并向用户提问。收到答复后重新执行整套基础信息预检。只有全部通过后，才能继续读取游客资料和分析分房。

基础信息通过时，明确告知用户：“基础信息已齐全，开始检查游客资料和分房方案。”

### 2. 读取游客资料和模板

1. 读取游客信息表、用户指定的分房模板、补充文字和图片。
2. 使用电子表格工具检查工作簿内容、合并单元格、字体、字号、行高、列宽、边框和日期格式。
3. 先渲染模板并目视检查；不得仅凭单元格值推断版式。用户提供参考截图时同时核对文字写法、标点、箭头、括号和表格截止位置。
4. 用户提供模板时优先使用该模板。没有提供模板时，使用 `assets/rooming-template.xlsx`。
5. 读取 `references/rooming-rules.md`、`references/template-spec.md` 和 `references/plan-schema.md`。

### 3. 执行详细制表前检查

逐项确认以下信息完整：

- 已通过基础信息预检的团号、领队、人数、领队信息和航班信息。
- 名单档号、行程名称和出发日期。
- 有领队时，核对领队中文名、英文名、性别、出生日期、出生地、护照号、签发日期、签发地、有效期和联系电话；明确无领队或导游时，核对 `leader: null`、人数后缀 `+0` 和顶部空白领队栏。
- 每位游客的订单号、原始备注、中文名、英文名、性别、出生日期、出生地、护照号、签发日期、签发地、有效期和联系电话。
- 所有截图更正、文字更正及其对应人员。
- 每条备注的实际含义、每个单数家庭的处理方式、所有单拼候选人的性别与成年状态。
- 最终房间数、各房人数、三人房、单住、跨订单拼房和领队安排。

出发日期不能可靠确定时必须询问用户，不得仅凭模糊团号猜测。不能从姓名推断领队或游客性别。有领队时，领队联系电话等必填项不得静默留空；只有用户明确确认无领队或导游时才允许按无领队流程处理。

### 4. 执行分房确认关卡

按照 `references/rooming-rules.md` 形成逐房方案，但先只在对话中整理方案，不生成表格。

遇到下列任一情况，停止并询问：

- 必填资料缺失或不同来源互相矛盾。
- 备注含义不清，或备注与未成年人、同性拼房等硬性规则冲突。
- 单数家庭中有多名符合条件的可拆分成年人，但未指定拆出谁。
- 单人订单为未成年人。
- 单拼池无法确定配对，或只能异性拼房。
- 用户给出的总人数、实际名单人数和房间占用人数不一致。
- 任何会改变客人住宿意愿、家庭拆分方式或房差安排的判断没有明确依据。

一次性列出全部已发现的问题，说明对应订单、人员、备注和可选处理方式。等待用户明确回复。收到补充后重新执行完整检查；只有全部问题关闭后，明确告知用户“资料完整、分房方案无冲突，开始制表”。

### 5. 生成已确认的分房计划

1. 为每个人分配唯一 `id`，不要用姓名作为唯一键。
2. 生成符合 `references/plan-schema.md` 的 JSON。
3. 房间顺序、房内人员顺序、家庭集中顺序和领队位置必须已经获得用户确认。
4. 将 `scripts/build_rooming_list.mjs` 复制到带有工作区依赖的临时工作目录，按脚本头部示例运行。
5. 输出文件名固定为 `{团号}分房名单.xlsx`。
6. 输出到当前任务的 `outputs` 目录，不覆盖用户原始文件。

脚本只执行已确认计划并验证硬性规则，不负责替用户解决含糊的分房决定。脚本报错时回到确认关卡，不得绕过验证。

### 6. 二次检查

导出后必须重新打开最终工作簿，并同时完成信息核对和版式核对。

信息核对：

- 游客人数、领队人数、房间数与顶部信息一致。
- 每个人恰好出现一次，无遗漏、重复或未知人员。
- 所有姓名、英文名、性别、生日、出生地、护照号、签发日期、签发地、有效期和电话与最终确认资料一致。
- 重新逐字段核对领队护照照片或用户文字，确保没有将模糊字符当作确定信息。
- 用户补充的每项更正均已应用。
- 未成年人没有跨订单单拼；跨订单拼房均为同性成年人。
- 领队位于最后，领队室友紧邻领队；如拆分家庭成员与领队拼房，整个家庭块位于末尾且仍连续。
- 同订单家庭的备注编号合并范围准确，不包含领队或其他订单人员。
- 房号连续，房型、每房人数、三人房和单住与确认方案一致。
- “用房数量”与实际房间数一致。
- 航班信息严格符合固定格式；只有用户明确要求时才允许其他写法。
- 扫描 `#REF!`、`#VALUE!`、`#DIV/0!`、`#NAME?`、`#N/A`。

版式核对：

- 渲染最终工作表并目视检查全部已用区域。
- 检查标题、表头、合并单元格、边框、对齐、行高、列宽、自动换行和分页观感。
- 检查文字、日期、护照号和电话号码没有截断、科学计数或丢失前导零。
- 逐列对照模板的非空示例单元格检查字体；尤其核对“出生地”和“签发日期”，不要以空白单元格的默认字体作为样式依据。
- 人员最后一行就是黑色表格的最后一行；其下不得残留内容、合并、边框、填充或其他表格格式。
- 最终预览必须包含人员末行之后至少 5 行，不能只裁切到已用数据区；逐格检查这 5 行没有黑线或格式残留。
- 修复后重新导出、重新打开并再次检查，直至信息和版式均通过。

### 7. 交付并汇报

交付最终 Excel 后，简要汇报：

- 总人数和总房数。
- 三人房、单人房和其他非标准房间。
- 每一组跨订单单拼人员及配对理由。
- 被拆分的家庭、拆出人员、原订单及拆分原因。
- 有领队时说明领队与谁拼房；若单住，说明没有合适的同性成年单拼游客。无领队或导游时明确说明顶部栏已保留为空且未生成 `TL` 行。
- 明确补房差单住、特殊备注等安排。
- 对每项特殊分房说明“遇到的情况”和“最终如何解决”。

没有特殊分房时也要明确写“本团无特殊分房安排”，不得省略汇报。
